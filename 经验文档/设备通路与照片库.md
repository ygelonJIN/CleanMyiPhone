# 设备通路与照片库

**什么时候读**：要接 iOS 设备（PTP / AFC / lockdownd / 私有框架）、要读 `Photos.sqlite`、要判断某个字段能不能拿到、或排查"读到 0 条 / 数量对不上"时，先读这篇。

**包含什么**：这台机器（macOS 27 + iPhone 14 Pro / iOS 26.7）上实测过的通路、键名、AFC 限制、照片库表结构与匹配策略、以及哪些数据第三方拿不到。

**不用读**：只改界面、只调版式时不用看。

---

## 一、三条通路分别能用什么

| 通路 | 能做什么 | 实测结论 |
|---|---|---|
| ImageCaptureCore（PTP） | 枚举媒体、设备端缩略图、大小/时间/时长、批量删除 | 4614 项枚举；512px 缩略图首张 104 ms |
| MobileDevice.framework（AFC） | 读 `/PhotoData/Photos.sqlite`、按路径取文件 | 296 MB 库下载 8 秒（≈36 MB/s） |
| lockdownd（经同一个私有框架） | 机型、系统版本、序列号、容量、电量、运营商 | 见下节键名 |

**`/var/run/usbmuxd` 的原始协议在 macOS 27 上已经不给第三方用**：连接能建立，发 `ListDevices`（v3–v6 都试过）和 `ReadBUID` 都直接被断开、零响应。不要在这条路上浪费时间，直接用 `dlopen("/System/Library/PrivateFrameworks/MobileDevice.framework/MobileDevice")`。

## 二、MobileDevice.framework 的关键签名

```c
int   AMDeviceNotificationSubscribe(callback, 0, 0, 0, &subscription);
int   AMDeviceConnect(device);
int   AMDeviceValidatePairing(device);
int   AMDeviceStartSession(device);
int   AMDeviceSecureStartService(device, CFStringRef name, CFDictionaryRef info, void **service);
int   AMDServiceConnectionGetSocket(void *service);
CFTypeRef AMDeviceCopyValue(device, CFStringRef domain, CFStringRef key);
AFCConnectionRef AFCConnectionCreate(alloc, int fd, uint8 secure, void *a, void *b);
int   AFCDirectoryOpen / AFCDirectoryRead / AFCDirectoryClose
int   AFCFileRefOpen / AFCFileRefRead / AFCFileRefClose
int   AMDServiceConnectionSend / Receive
```

坑：

1. `AMDeviceNotification` 的结构是 `{ am_device *dev; uint32 msg; notification *sub; }`，`dev` 在 **偏移 0**、`msg` 在 **偏移 8**，`msg == 1` 表示已连接。
2. `AMDeviceSecureStartService` 的第四参是 **service connection**，要再调 `AMDServiceConnectionGetSocket` 拿 fd；直接当 int 用会得到无效 socket，AFC 一律返回 `NOT_SUPPORTED(11)`。
3. **AFC 单次读上限 256 KB**。1 MB 会返回 `READ_ERROR(4)`，而且此时 `length` 是脏值，切片前必须 clamp，否则越界崩溃。
4. 通知只往**主 RunLoop** 投递：把整个读取流程丢到后台线程会永远等不到设备。正确做法是主线程分片读、每 N 片 `await Task.yield()`。
5. `AMDeviceCopyValue(device, nil, nil)` 能拿到整个基础域的 72 个键，排查键名时直接 dump 比猜快。

## 四、PhotoData / Photos.sqlite

- `/PhotoData` 与 `/DCIM` 在 AFC 根下都能列出来；`/PhotoData/Photos.sqlite` 可直接读（296 MB，无 WAL 时为单文件）。
- 表：`ZASSET`（`Z_PK/ZUUID/ZFILENAME/ZDIRECTORY/ZDATECREATED/ZKIND/ZKINDSUBTYPE/ZHIDDEN/ZFAVORITE/ZTRASHEDSTATE/ZWIDTH/ZHEIGHT/ZDURATION`）、`ZADDITIONALASSETATTRIBUTES`（`ZORIGINALFILESIZE` 等）、`ZGENERICALBUM`（相簿，`ZTITLE/ZKIND/ZCACHEDCOUNT`）。
- **相簿↔资产关联表名随版本变**（本机是 `Z_33ASSETS`，两列 `Z_33ALBUMS` / `Z_3ASSETS`）。不要写死：扫 `Z_%ASSETS`，找列名以 `ALBUMS`/`ASSETS` 结尾的表，再用"能不能对上 `ZGENERICALBUM.Z_PK`"校验。
- `ZKIND`：0 照片、1 视频。`ZKINDSUBTYPE` 实测 10 = 截图（1179×2556 PNG，等于 iPhone 14 Pro 屏宽），1 = 全景候选，100/103 = 视频变体，2 = 仍未校准（约 1900 项 HEIC）。
- 相簿 `ZKIND=2` 是用户/来源相簿（实测有「带饭」「微信」「抖音」「PS App」等），`1506` 是一批无标题项。
- 本机实测规模：`ZASSET` 5270 行，隐藏 124、收藏 50、最近删除 4，相簿 21 个。

## 五、跨通路匹配（最容易踩的坑）

PTP 报的 `name` **不等于磁盘上的文件名**：实测 PTP 给 `CUJR5109.MOV`，库里同编号的是 `IMG_5109.JPG`；`OVNL2344.MP4` 这类随机前缀也会出现。因此：

1. 先按归一化文件名匹配（小写 + `IMG_E1234` → `IMG_1234`，编辑版在 PTP 里带 `_E`）；
2. 再按 **`fileSize` + `creatingDate`（前后 2 秒）** 去 `ZORIGINALFILESIZE/ZDATECREATED` 上匹配；
3. 命中率从 75.6% 提到 79.6%，剩下的是 App 保存的随机名文件。

取视频文件播放时同理：先用库里的真实 `ZFILENAME` 去 DCIM 里找，再用 PTP 名字，最后按"数字 + 扩展名"兜底。

## 六、明确拿不到的东西（不要再试）

| 想拿 | 尝试过 | 结论 |
|---|---|---|
| 单个 App 体积 | `installation_proxy` 的 `Lookup`/`Browse`（含分块读 `CurrentList`） | iOS 26 只回元数据，没有 `StaticDiskUsage`/`DynamicDiskUsage` |
| App 图标 | `com.apple.springboardservices` → `getIconPNGData` | 返回空，通道对第三方关闭 |
| 电话号码 | lockdown `PhoneNumber` / `phone_number` | 空 |
| 设备截图 | `com.apple.screenshotr` | 设备锁屏时返回错误码，解锁后可用 |

同类商业工具 能做这三样，是因为它装了被系统信任的特权辅助进程，不是公开 API 的能力。

## 七、删除相关的已知结论

- 第三方删除**不进"最近删除"**，照片是永久消失。
- 开了 iCloud 照片时会返回 `ICDeleteErrorReadOnly`，只能在本机相册删。
- 删除通道用 `ICCameraFile.requestDeleteFiles:deleteFailed:completion:`；`ICDeleteResult.successful` 拿成功列表。
- `ICCameraFile.requestDownloadWithOptions:completion:` 在本机直接抛 ObjC 异常（选项字典类型不匹配）导致 abort，**不要用**；取原文件走 AFC 分片读。

## 八、相册库快照：必须整搬「四件套」

**一句话**：`Photos.sqlite` 是 WAL 模式，主文件 + `-wal` + `-shm` 三件才构成一致快照；只拷主文件必然 `database disk image is malformed`，一条都读不出来。

要拷的四件：

| 设备路径 | 本地名字 | 说明 |
|---|---|---|
| `/PhotoData/Photos.sqlite` | `Photos.sqlite` | 主库，约 296 MB |
| `/PhotoData/Photos.sqlite-wal` | `Photos.sqlite-wal` | 未合并的写入，大小随时变 |
| `/PhotoData/Photos.sqlite-shm` | `Photos.sqlite-shm` | WAL 索引，缺了本地打开要重建 |
| `/PhotoData/Thumbnails/thumbnailConfiguration` | `thumbnailConfiguration` | 约 499 B 的 plist，缩略图规格，可选 |

打开方式：`sqlite3_open_v2("file:...?mode=rw", SQLITE_OPEN_READWRITE | SQLITE_OPEN_URI)`。
**不要 `immutable=1`**——它会直接忽略 WAL，等于只读主文件。验收用 `PRAGMA quick_check` 拿到 `ok`，再用 `SELECT count(*) FROM ZASSET` 确认行数（本机 5270）。

### 四个坑（按踩到的顺序）

1. **不要用 seek / fileSize 判断「读全了没有」**
   `AFCFileRefSeek` 跳到末尾再 `tell` 得到 296,542,208，但顺序读只能读到 292,610,048——两者不是一回事；用 seek 的大小做完整性判断，会把正常快照误判成「缺 3.9 MB」。更糟的是 seek 之后接着读会错位，字节数对、内容错，SQLite 报 malformed。

2. **`status == 0 && length == 0` 不等于文件尾**
   USB 通道会瞬时没数据。等 10–30 ms 重读就能继续（实测从 292,610,048 一路读到 296,542,208，1132 片）。连续 400 次 0 读再当 EOF。

3. **PTP 会话存在时 AFC 读不到**
   `ICDeviceBrowser` 一被构造，icdd 就占住设备，AFC `AFCFileRefOpen` 失败、读回 0 字节，甚至把进程写崩。
   正确顺序：**先读库**（此时还没有任何 ImageCaptureCore 对象）→ 再启 PTP 枚举照片；重试读库时临时 `ptp.stop()` 再 `start()`。`ICDeviceBrowser` 要做成懒创建。

4. **下载放子进程**
   同样四件套，在主进程里读会在 8–292 MB 之间随机 SIGSEGV（栈落在 libdispatch / Swift 字符串分配，看起来像界面崩溃）。放到子进程（`--fetch-library <path>`）就稳。
   子进程里不要初始化 AppKit / ICDeviceBrowser：`CleanMyiPhoneApp.init` 必须在建 `AppStore` **之前**判断 `--fetch-library` 并 `exit`，否则子进程也会拉起 ImageCaptureCore 和它自己抢设备。

### 重试与缓存

- 失败只重抓 `-wal` / `-shm` 并重新 `quick_check`（几百毫秒），主库不重下；最多 3 次。
- 验证不过就保留上一份可用快照，不要删好副本。
- 本地缓存：`~/Library/Application Support/cleanmyiphone/`，6 小时内复用；PTP 枚举完成后，若设备上有比快照更新的照片（差 > 120 秒），后台自动重抓一次。
- 删掉这个目录 = 回到「新机」状态，下次启动会重新拉 296 MB。

## 九、iOS 26.7 实测：三条新结论（决定界面能写多满）

用 `--probe-keys` / `--probe-battery` / `--probe-house` 三个探针在 iPhone 14 Pro / iOS 26.7 上跑出来的。

### 1. house_arrest 对第三方关闭 —— App 容器一律打不开

```
{"Command":"VendContainer","Identifier":"com.tencent.xin"}  -> Error: InstallationLookupFailed
{"Command":"VendDocuments","Identifier":"com.tencent.xin"}  -> Error: InstallationLookupFailed
{"Command":"VendContainer","ApplicationIdentifier":"..."}    -> Error: MissingIdentifier
```

- 键名没错：写错键会回 `MissingIdentifier`，写对了才回 `InstallationLookupFailed`。
- **微信、Apple 自家的「文件」App（com.apple.DocumentsApp）全都一样**，不是个例。
- 结论：**App 沙盒容器、各 App 的「文稿与数据」、文件 App 的「我的 iPhone / 下载」全都拿不到。**
  同类商业工具 能做是因为它装了一条被系统信任的特权辅助进程。
- 副作用：不要把「应用文稿」做成会转圈的功能，直接显示 `—` 并说明原因。

### 2. 电池细项走 diagnostics_relay 的 `GasGauge`（不是 IORegistry）

```
{"Request":"GasGauge"} -> Diagnostics.GasGauge = {
    DesignCapacity: 3181, FullChargeCapacity: 100, CycleCount: 1516, Status: Success
}
```

- **`DesignCapacity` 是 mAh**（设计最大电量）。
- **`FullChargeCapacity` 在 iOS 26 上给的是百分比**（100 = 100% 健康），不是 mAh；`>100` 时才当 mAh 用。
- 有效最大电量 = 设计 × 健康百分比。
- `IORegistry` 那条路（`AppleSmartBattery` / `IOPMPowerSource`）只回一棵一层树（`children: [D73AP]`），**温度拿不到**；`{"Request":"All"}` 里也只有 GasGauge / HDMI / NAND / WiFi 四项。
- 所以「电池温度」这一行只能写不可读，别编数字。

### 3. lockdownd 那几个键确认可用

- `ModelNumber`（基础域）→ `MQ0W3`，可用。
- `PasswordProtected` / `DeviceLocked` → 锁屏判定用它，锁屏就不用傻等 180 秒超时。
- `AMDeviceCopyValue(device, nil, nil)` 基础域 72 个键里**没有** Apple 账户，也没有电话号码。

### 4. AFC 根（`/var/mobile/Media`）里到底有什么

`AirFair / Airlock / Books / CloudAssets / DCIM / Deferred / Downloads / EnhancedAudioSharedKeys /
Espresso / 同类商业工具 / iTunes_Control / ManagedPurchases / MediaAnalysis / Music / PhotoData / Photos /
PhotoStreamsData / Podcasts / PublicStaging / Purchases / Radio / Recordings / …`

真正的「文件」页只能做这块：相机胶卷原文件、录音、电子书、铃声、播客。顺带发现根下有个 `Downloads`，
可以进去看看是不是文件 App 的下载目录（待验）。

### 5. 应用清单能拿到什么、拿不到什么（`--probe-appsize` 实测）

`installation_proxy` 的 `Lookup` 在 iOS 26.7 上返回 321 条，每条字段很全，但关键的几项是空的：

| 想要 | 结果 |
|---|---|
| `BundleSize` / `FileSize` | **nil** |
| `StaticDiskUsage` / `DynamicDiskUsage` | **nil** |
| `Path` | ✅ `/private/var/containers/Bundle/Application/<UUID>/WeChat.app` |
| `Container` | ✅ `/private/var/mobile/Containers/Data/Application/<UUID>` |
| `CFBundleIcons` | ✅ `{ CFBundlePrimaryIcon = { CFBundleIconFiles = (AppIcon60x60) } }` |
| `ApplicationType` | ✅ `User` 61 / `System` 237 / `Hidden` 23 |

结论：

- **体积拿不到**：字段在，值是 nil，换三组 Attributes 都一样。
- **图标拿不到**：图标文件名拿到了（`AppIcon60x60`，实际文件是 `AppIcon60x60@2x.png`），
  但文件在 `/private/var/containers/...`，数据线通道只到 `/var/mobile/Media`，house_arrest 又关了。
- **只显示 `ApplicationType == "User"`**：`Hidden`（CarPlay、Bridge 这类）和 `System` 都别当用户 App。
  之前用 `type == "System"` 判断，会把 23 个 Hidden 漏进列表。
- 唯一「看起来像体积」的替代方案是走完整备份（`Manifest.plist` 里有每个 App 的字节数），
  但那要先做一次全量备份，属于另一个量级的功能。

### 6. 会话泄漏会把 PTP 一起搞挂

`try MobileDeviceAPI()` 每 new 一次都会重新 `AMDeviceNotificationSubscribe` + `AMDeviceConnect`，
**连了不 disconnect**。多来几次之后 icdd 的 PTP 会话会被顶掉，表现是「照片列表出来了，
但缩略图和空格预览一直转圈、图永远不出来」。

修法（已落地）：

1. `MobileDeviceAPI.shared()` 单例，`openSession` 幂等（`connected` / `sessionOpened` 两个标志）。
2. 缩略图请求加 8 秒看门狗，超时返回 nil，不让界面无限转圈。
3. 预览取不到 PTP 大图时，降级用 AFC 把原文件整份拉回来再解码。

### 7. 缩略图：V2 缓存是 0 字节，只能走 AFC 下原图

`--probe-thumbdir` 实测（iPhone 14 Pro / iOS 26.7）：

```
/PhotoData/Thumbnails          6 项：3307.ithmb 3324.ithmb 4531.ithmb V2 VideoKeyFrames thumbnailConfiguration
/PhotoData/Thumbnails/V2       2 项：DCIM  PhotoData
   DCIM/                       43 项：100APPLE 101APPLE …
     100APPLE/                 54 项：IMG_0005.JPG IMG_0017.JPG …
        样例 …/IMG_0005.JPG     entrySize 0，readFile 0 字节 → 缓存文件是空的
对照 /DCIM/100APPLE/IMG_0005.JPG  一次读到 262144 字节（正常）
```

结论：

1. **V2 里镜像了 DCIM 目录结构**（`Thumbnails/V2/<ZDIRECTORY>/<ZFILENAME>`），
   但文件是 0 字节（iOS 26 上这层缓存没内容，真正的缩略图在 `*.ithmb` 里，那是 Apple 私有容器格式）。
2. **AFC 读原图是通的**，而且不被 App 自己的 PTP 会话堵住（实测：App 在跑，探针照样读到 262 KB）。
3. 所以网格缩略图的可行路线是：**AFC 下原图 → ImageIO 降采样 → 落盘缓存**。
   已按这个实现（`DeviceFiles.thumbnail`），PTP 那条留着当快车道，失败就降级。
4. `readFile` 有一个**会崩**的老坑：AFC 回 0 长度时 `length` 是脏值，`buffer[0..<Int(length)]` 直接
   `Fatal error: Array index is out of range`。必须 `min(Int(length), chunk)` 之后再切片。
