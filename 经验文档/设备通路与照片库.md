# 设备通路与照片库

**什么时候读**：要接 iOS 设备（PTP / AFC / lockdownd / 私有框架）、要读 `Photos.sqlite`、要判断某个字段能不能拿到、或排查"读到 0 条 / 数量对不上"时，先读这篇。

**包含什么**：这台机器（macOS 27 + iPhone 14 Pro / iOS 26.7）上实测过的通路、键名、AFC 限制、照片库表结构与匹配策略、以及哪些数据第三方拿不到。

**不用读**：只改界面、只调版式时不用看。

---

## 一、三条通路分别能用什么

| 通路 | 能做什么 | 实测结论 |
|---|---|---|
| ImageCaptureCore（PTP） | 枚举媒体、设备端缩略图、大小/时间/时长、批量删除 | 4614 项枚举；512px 缩略图首张 104 ms |
| MobileDevice.framework（AFC） | 读 `/PhotoData/Photos.sqlite`、按路径取文件 | 296 MB 库下载 8 秒（≈36 MB/s） |
| lockdownd（经同一个私有框架） | 机型、系统版本、序列号、容量、电量、运营商 | 见下节键名 |

**`/var/run/usbmuxd` 的原始协议在 macOS 27 上已经不给第三方用**：连接能建立，发 `ListDevices`（v3–v6 都试过）和 `ReadBUID` 都直接被断开、零响应。不要在这条路上浪费时间，直接用 `dlopen("/System/Library/PrivateFrameworks/MobileDevice.framework/MobileDevice")`。

## 二、MobileDevice.framework 的关键签名

```c
int   AMDeviceNotificationSubscribe(callback, 0, 0, 0, &subscription);
int   AMDeviceConnect(device);
int   AMDeviceValidatePairing(device);
int   AMDeviceStartSession(device);
int   AMDeviceSecureStartService(device, CFStringRef name, CFDictionaryRef info, void **service);
int   AMDServiceConnectionGetSocket(void *service);
CFTypeRef AMDeviceCopyValue(device, CFStringRef domain, CFStringRef key);
AFCConnectionRef AFCConnectionCreate(alloc, int fd, uint8 secure, void *a, void *b);
int   AFCDirectoryOpen / AFCDirectoryRead / AFCDirectoryClose
int   AFCFileRefOpen / AFCFileRefRead / AFCFileRefClose
int   AMDServiceConnectionSend / Receive
```

坑：

1. `AMDeviceNotification` 的结构是 `{ am_device *dev; uint32 msg; notification *sub; }`，`dev` 在 **偏移 0**、`msg` 在 **偏移 8**，`msg == 1` 表示已连接。
2. `AMDeviceSecureStartService` 的第四参是 **service connection**，要再调 `AMDServiceConnectionGetSocket` 拿 fd；直接当 int 用会得到无效 socket，AFC 一律返回 `NOT_SUPPORTED(11)`。
3. **AFC 单次读上限 256 KB**。1 MB 会返回 `READ_ERROR(4)`，而且此时 `length` 是脏值，切片前必须 clamp，否则越界崩溃。
4. 通知只往**主 RunLoop** 投递：把整个读取流程丢到后台线程会永远等不到设备。正确做法是主线程分片读、每 N 片 `await Task.yield()`。
5. `AMDeviceCopyValue(device, nil, nil)` 能拿到整个基础域的 72 个键，排查键名时直接 dump 比猜快。

## 四、PhotoData / Photos.sqlite

- `/PhotoData` 与 `/DCIM` 在 AFC 根下都能列出来；`/PhotoData/Photos.sqlite` 可直接读（296 MB，无 WAL 时为单文件）。
- 表：`ZASSET`（`Z_PK/ZUUID/ZFILENAME/ZDIRECTORY/ZDATECREATED/ZKIND/ZKINDSUBTYPE/ZHIDDEN/ZFAVORITE/ZTRASHEDSTATE/ZWIDTH/ZHEIGHT/ZDURATION`）、`ZADDITIONALASSETATTRIBUTES`（`ZORIGINALFILESIZE` 等）、`ZGENERICALBUM`（相簿，`ZTITLE/ZKIND/ZCACHEDCOUNT`）。
- **相簿↔资产关联表名随版本变**（本机是 `Z_33ASSETS`，两列 `Z_33ALBUMS` / `Z_3ASSETS`）。不要写死：扫 `Z_%ASSETS`，找列名以 `ALBUMS`/`ASSETS` 结尾的表，再用"能不能对上 `ZGENERICALBUM.Z_PK`"校验。
- `ZKIND`：0 照片、1 视频。`ZKINDSUBTYPE` 实测 10 = 截图（1179×2556 PNG，等于 iPhone 14 Pro 屏宽），1 = 全景候选，100/103 = 视频变体，2 = 仍未校准（约 1900 项 HEIC）。
- 相簿 `ZKIND=2` 是用户/来源相簿（实测有「带饭」「微信」「抖音」「PS App」等），`1506` 是一批无标题项。
- 本机实测规模：`ZASSET` 5270 行，隐藏 124、收藏 50、最近删除 4，相簿 21 个。

## 五、跨通路匹配（最容易踩的坑）

PTP 报的 `name` **不等于磁盘上的文件名**：实测 PTP 给 `CUJR5109.MOV`，库里同编号的是 `IMG_5109.JPG`；`OVNL2344.MP4` 这类随机前缀也会出现。因此：

1. 先按归一化文件名匹配（小写 + `IMG_E1234` → `IMG_1234`，编辑版在 PTP 里带 `_E`）；
2. 再按 **`fileSize` + `creatingDate`（前后 2 秒）** 去 `ZORIGINALFILESIZE/ZDATECREATED` 上匹配；
3. 命中率从 75.6% 提到 79.6%，剩下的是 App 保存的随机名文件。

取视频文件播放时同理：先用库里的真实 `ZFILENAME` 去 DCIM 里找，再用 PTP 名字，最后按"数字 + 扩展名"兜底。

## 六、明确拿不到的东西（不要再试）

| 想拿 | 尝试过 | 结论 |
|---|---|---|
| 单个 App 体积 | `installation_proxy` 的 `Lookup`/`Browse`（含分块读 `CurrentList`） | iOS 26 只回元数据，没有 `StaticDiskUsage`/`DynamicDiskUsage` |
| App 图标 | `com.apple.springboardservices` → `getIconPNGData` | 返回空，通道对第三方关闭 |
| 电话号码 | lockdown `PhoneNumber` / `phone_number` | 空 |
| 设备截图 | `com.apple.screenshotr` | 设备锁屏时返回错误码，解锁后可用 |

同类商业工具 能做这三样，是因为它装了被系统信任的特权辅助进程，不是公开 API 的能力。

**界面处理**：右侧栏已经不再为这三项留「不可读」占位，直接不显示——占位行会让人以为是没读到、反复去试。
iMazing 二进制里的 `BatteryTemperature` / `BatteryMaximumTemperature` 之类标签配的是 `BatteryDiagnostic.json`（设备端诊断产物）+ `exportIORegistry`（递归导 IORegistry），
GasGauge 那条路只有 DesignCapacity / FullChargeCapacity / CycleCount，**没有温度**；想试就单独开一次 IORegistry 深挖探针，别在界面上留半成品。

## 七、删除相关的已知结论

- 第三方删除**不进"最近删除"**，照片是永久消失。
- 开了 iCloud 照片时会返回 `ICDeleteErrorReadOnly`，只能在本机相册删。
- 删除通道用 `ICCameraFile.requestDeleteFiles:deleteFailed:completion:`；`ICDeleteResult.successful` 拿成功列表。
- `ICCameraFile.requestDownloadWithOptions:completion:` 在本机直接抛 ObjC 异常（选项字典类型不匹配）导致 abort，**不要用**；取原文件走 AFC 分片读。

## 八、相册库「四件套」：只作中转，读完立刻删

> **2026-11 改：不再做本地快照。** 用户的硬要求是「零痕迹」，而 296 MB 的照片库副本
> 就是最大的痕迹；那个「6 小时内复用」的缓存也因为启动第一步就删文件而**从来没命中过**。
> 现在的做法：四件套下到数据目录 → `PhotoLibraryIndex.load` 读进内存 →
> `LibraryService.purgeSnapshotFiles()` 立刻删（失败路径也删）。代价是每次启动重读一遍，
> 后台读、界面照常用。下面这些结论仍然是**怎么把四件套完整搬下来**的必需知识，别删。

**一句话**：`Photos.sqlite` 是 WAL 模式，主文件 + `-wal` + `-shm` 三件才构成一致快照；只拷主文件必然 `database disk image is malformed`，一条都读不出来。

要搬的四件（中转用，读完即删）：

| 设备路径 | 本地名字 | 说明 |
|---|---|---|
| `/PhotoData/Photos.sqlite` | `Photos.sqlite` | 主库，约 296 MB |
| `/PhotoData/Photos.sqlite-wal` | `Photos.sqlite-wal` | 未合并的写入，大小随时变 |
| `/PhotoData/Photos.sqlite-shm` | `Photos.sqlite-shm` | WAL 索引，缺了本地打开要重建 |
| `/PhotoData/Thumbnails/thumbnailConfiguration` | `thumbnailConfiguration` | 约 499 B 的 plist，缩略图规格，可选 |

打开方式：`sqlite3_open_v2("file:...?mode=rw", SQLITE_OPEN_READWRITE | SQLITE_OPEN_URI)`。
**不要 `immutable=1`**——它会直接忽略 WAL，等于只读主文件。验收用 `PRAGMA quick_check` 拿到 `ok`，再用 `SELECT count(*) FROM ZASSET` 确认行数（本机 5270）。

### 四个坑（按踩到的顺序）

1. **不要用 seek / fileSize 判断「读全了没有」**
   `AFCFileRefSeek` 跳到末尾再 `tell` 得到 296,542,208，但顺序读只能读到 292,610,048——两者不是一回事；用 seek 的大小做完整性判断，会把正常快照误判成「缺 3.9 MB」。更糟的是 seek 之后接着读会错位，字节数对、内容错，SQLite 报 malformed。

2. **`status == 0 && length == 0` 不等于文件尾**
   USB 通道会瞬时没数据。等 10–30 ms 重读就能继续（实测从 292,610,048 一路读到 296,542,208，1132 片）。

   **但别把这句照搬到所有下载上**：曾经照着写了「不看状态码、一律空读 400 次、每次 sleep 30ms」，
   结果**每个文件固定多花 12 秒**（400×30ms），几百 KB 的缩略图也一样 —— 网格缩略图慢到像坏了就是它。
   正确写法（`DeviceFiles.downloadLocked` 已改）：
   ```swift
   if let chunk = readChunk { 写入; stalled = 0; continue }
   if lastReadStatus == 0 { break }   // status 0 + 0 字节 = 正常文件尾，立刻结束
   stalled += 1; if stalled > 3 { break }   // 只有真·读错误才退避
   usleep(20_000)
   ```
   大文件（`Photos.sqlite`）照样能续读到最后一字节，小文件不用再为 EOF 陪跑 12 秒。

3. **PTP 会话存在时 AFC 读不到**
   `ICDeviceBrowser` 一被构造，icdd 就占住设备，AFC `AFCFileRefOpen` 失败、读回 0 字节，甚至把进程写崩。
   正确顺序：**先读库**（此时还没有任何 ImageCaptureCore 对象）→ 再启 PTP 枚举照片；重试读库时临时 `ptp.stop()` 再 `start()`。`ICDeviceBrowser` 要做成懒创建。

4. **下载放子进程**
   同样四件套，在主进程里读会在 8–292 MB 之间随机 SIGSEGV（栈落在 libdispatch / Swift 字符串分配，看起来像界面崩溃）。放到子进程（`--fetch-library <path>`）就稳。
   子进程里不要初始化 AppKit / ICDeviceBrowser：`CleanMyiPhoneApp.init` 必须在建 `AppStore` **之前**判断 `--fetch-library` 并 `exit`，否则子进程也会拉起 ImageCaptureCore 和它自己抢设备。

### 重试与缓存

- 失败只重抓 `-wal` / `-shm` 并重新 `quick_check`（几百毫秒），主库不重下；最多 3 次。
- 验证不过就保留上一份可用快照，不要删好副本。
- 本地缓存：`~/Library/Application Support/cleanmyiphone/`，6 小时内复用；PTP 枚举完成后，若设备上有比快照更新的照片（差 > 120 秒），后台自动重抓一次。
- 删掉这个目录 = 回到「新机」状态，下次启动会重新拉 296 MB。

## 九、iOS 26.7 实测：三条新结论（决定界面能写多满）

用 `--probe-keys` / `--probe-battery` / `--probe-house` 三个探针在 iPhone 14 Pro / iOS 26.7 上跑出来的。

### 1. house_arrest 对第三方关闭 —— App 容器一律打不开

```
{"Command":"VendContainer","Identifier":"com.tencent.xin"}  -> Error: InstallationLookupFailed
{"Command":"VendDocuments","Identifier":"com.tencent.xin"}  -> Error: InstallationLookupFailed
{"Command":"VendContainer","ApplicationIdentifier":"..."}    -> Error: MissingIdentifier
```

- 键名没错：写错键会回 `MissingIdentifier`，写对了才回 `InstallationLookupFailed`。
- **微信、Apple 自家的「文件」App（com.apple.DocumentsApp）全都一样**，不是个例。
- 结论：**App 沙盒容器、各 App 的「文稿与数据」、文件 App 的「我的 iPhone / 下载」全都拿不到。**
  同类商业工具 能做是因为它装了一条被系统信任的特权辅助进程。
- 副作用：不要把「应用文稿」做成会转圈的功能，直接显示 `—` 并说明原因。

### 2. 电池细项走 diagnostics_relay 的 `GasGauge`（不是 IORegistry）

```
{"Request":"GasGauge"} -> Diagnostics.GasGauge = {
    DesignCapacity: 3181, FullChargeCapacity: 100, CycleCount: 1516, Status: Success
}
```

- **`DesignCapacity` 是 mAh**（设计最大电量），**`CycleCount`** 是循环次数 —— 这两个可信。
- **`FullChargeCapacity` 给的是 `100`**，那是**满充百分比，不是健康度**。早先把它当健康度算，界面就永远显示 100%（循环 1516 次的机器显然不是 100%）。现在只有 `>1000` 才当 mAh 用，否则忽略。
- **IORegistry 这条路走不通**：每次 `{"Request":"IORegistry"}` 只回 `children=1`、`regEntry` 为空，按名字点名（`AppleSmartBattery` / `AppleARMPMUCharger` / `pmu` / `battery`，名字和 class 都试过）也一样。现场记录在 `~/Library/Application Support/cleanmyiphone/battery-dump.txt`。
- `{"Request":"All"}` 只有 GasGauge / HDMI / NAND / WiFi 四项。
- 结论：**真实电池容量/健康度、电池温度都拿不到**。iMazing 那边是靠导出 `BatteryDiagnostic.json`（设备端诊断产物，几十秒到几分钟、要解锁），属于"按需"，不适合放在右侧栏常驻。界面因此不显示这些行，不留 `—` 占位。

### 3. lockdownd 那几个键确认可用

- `ModelNumber`（基础域）→ `MQ0W3`，可用。
- `PasswordProtected` / `DeviceLocked` → 锁屏判定用它，锁屏就不用傻等 180 秒超时。
- `AMDeviceCopyValue(device, nil, nil)` 基础域 72 个键里**没有** Apple 账户，也没有电话号码。

### 4. AFC 根（`/var/mobile/Media`）里到底有什么

`AirFair / Airlock / Books / CloudAssets / DCIM / Deferred / Downloads / EnhancedAudioSharedKeys /
Espresso / 同类商业工具 / iTunes_Control / ManagedPurchases / MediaAnalysis / Music / PhotoData / Photos /
PhotoStreamsData / Podcasts / PublicStaging / Purchases / Radio / Recordings / …`

真正的「文件」页只能做这块：相机胶卷原文件、录音、电子书、铃声、播客。顺带发现根下有个 `Downloads`，
可以进去看看是不是文件 App 的下载目录（待验）。

### 5. 应用清单能拿到什么、拿不到什么（`--probe-appsize` 实测）

`installation_proxy` 的 `Lookup` 在 iOS 26.7 上返回 321 条，每条字段很全，但关键的几项是空的：

| 想要 | 结果 |
|---|---|
| `BundleSize` / `FileSize` | **nil** |
| `StaticDiskUsage` / `DynamicDiskUsage` | **nil** |
| `Path` | ✅ `/private/var/containers/Bundle/Application/<UUID>/WeChat.app` |
| `Container` | ✅ `/private/var/mobile/Containers/Data/Application/<UUID>` |
| `CFBundleIcons` | ✅ `{ CFBundlePrimaryIcon = { CFBundleIconFiles = (AppIcon60x60) } }` |
| `ApplicationType` | ✅ `User` 61 / `System` 237 / `Hidden` 23 |

结论：

- **体积拿不到**：字段在，值是 nil，换三组 Attributes 都一样。
- **图标拿不到**：图标文件名拿到了（`AppIcon60x60`，实际文件是 `AppIcon60x60@2x.png`），
  但文件在 `/private/var/containers/...`，数据线通道只到 `/var/mobile/Media`，house_arrest 又关了。
- **只显示 `ApplicationType == "User"`**：`Hidden`（CarPlay、Bridge 这类）和 `System` 都别当用户 App。
  之前用 `type == "System"` 判断，会把 23 个 Hidden 漏进列表。
- 唯一「看起来像体积」的替代方案是走完整备份（`Manifest.plist` 里有每个 App 的字节数），
  但那要先做一次全量备份，属于另一个量级的功能。

### 6. 会话泄漏会把 PTP 一起搞挂

`try MobileDeviceAPI()` 每 new 一次都会重新 `AMDeviceNotificationSubscribe` + `AMDeviceConnect`，
**连了不 disconnect**。多来几次之后 icdd 的 PTP 会话会被顶掉，表现是「照片列表出来了，
但缩略图和空格预览一直转圈、图永远不出来」。

修法（已落地）：

1. `MobileDeviceAPI.shared()` 单例，`openSession` 幂等（`connected` / `sessionOpened` 两个标志）。
2. 缩略图请求不再干等：`thumbnail(for:)` 主动发请求 + 1.5 秒超时 + 连续 3 次失败就关掉这条捷径（详见第九节第 7 条）。
3. 预览取不到就用 AFC 把原文件整份拉回来再解码。

### 7. 缩略图：走**设备端缩略图**，不要去下原图

设备自己的缩略图缓存目录是空的（`/PhotoData/Thumbnails/V2` 里镜像了 DCIM 结构但文件 0 字节，真正的缩略图在 Apple 私有的 `*.ithmb` 里），
所以一度以为"只能 AFC 下原图再降采样" —— **这个结论是错的，代价是每张图都要下 2–4 MB**。

正确的做法是 ImageCaptureCore 的缩略图请求，`ICCameraItem.h` 写得很清楚：

> `thumbnail` 属性的值是 **NULL，除非给这个对象发过 `requestThumbnail`**。
> `requestThumbnail` 会向设备请求缩略图，结果通过 `cameraDevice:didReceiveThumbnail:forItem:error:` 回来。

落地要点（`PTPBridge.swift`）：

1. 实现 `cameraDevice(_:shouldGetThumbnailOf:)` 返回 `true`，让框架在枚举时顺手取；
2. 主动发 `requestThumbnailData(options: [.imageSourceThumbnailMaxPixelSize: 800])`
   —— **不能同时传 `.imageSourceShouldCache`**，SDK 原文："Use of this key will override any custom thumbnail size requested, ignoring the ICImageSourceThumbnailMaxPixelSize option entirely"，
   两个一起传拿回来的就是 160×120 的 EXIF 标准尺寸，网格里糊成一片；
3. 挂等待者等 delegate 回填，1.5 秒超时；**连续 3 次超时就关掉这条捷径**（熔断），否则每张图都陪跑一个超时；
4. 收到就存内存 + 落 480px JPEG 磁盘缓存，之后都是本地读；
5. 视频也吃这一套（设备对视频同样返回海报帧），所以网格里**永远不要为了缩略图去下整段视频**。

`readFile` 有个**会崩**的老坑仍然成立：AFC 回 0 长度时 `length` 是脏值，
`buffer[0..<Int(length)]` 直接 `Fatal error: Array index out of range`。
必须 `min(Int(length), chunk)` 之后再切片。


### 8. 预览取原文件：按库里的绝对路径走 AFC

预览（空格）要的是**原始文件**，路径不要靠猜：

- 相册库里就有 `'/' || ZDIRECTORY || '/' || ZFILENAME`，直接拼成 `/DCIM/100APPLE/IMG_0005.HEIC` 走 AFC，实测 **36 MB/s**（100 MB 的视频 3 秒）。
- 拿不到库（还没读到 / 已清空）时才退 `ICCameraFile.requestDownload(options:completion:)`：它按设备对象句柄取，不需要文件名匹配，但走的是 PTP 单流小包，几十 MB 以上的视频会慢到超时。
- 最后一道才是"拿 PTP 名字去 /DCIM 索引里匹配"，命中率低（`CUJR5109.MOV` vs `IMG_5109.JPG`），失败信息要带上索引条目数，方便区分"没建索引"还是"名字对不上"。
- 进度分母必须用**设备报的真实大小**（打开文件后 `AFCFileRefSeek`+Tell）。PTP 的 `fileSize` 对大视频经常偏大，拿它当分母就会卡在 `90.4 MB / 118.3 MB` 不动、其实文件早已经取完。
- 半截文件绝不能留在缓存里：切换预览目标时要把上一条下载**作废**（每个分块检查一次令牌），被作废的和不完整的都直接删掉，否则下次播放就是"播放不可用"。
- **令牌写在 `if previewID != id` 里等于没写**（2026-11 实测踩过）：`openPreview` / `stepPreview` / `move` 都是「先给 `previewID` 赋新值、再调 `loadPreviewImage(for:)`」，进到函数里那个判断恒为 false，`cancelPreviewDownload()` 一次都没执行过。后果是关掉或换目标后旧视频继续占着那条串行下载队列跑到收尾，新视频排在它后面，界面看着就是"打开了却没反应"。改成在 `loadPreviewImage` 顶部**无条件**作废，`closePreview()` 也调一次。
- **进度回调必须归属**：`onProgress(done, total)` 里先 `guard previewID == id` 再写界面状态，否则旧下载每读一个 256 KB 分块就把自己的字节数写进共享字段，新预览上显示的还是上一个视频的数字。`waitForLibraryIndex` 也要传 `for: id`，换目标就停写阶段文案。
- **完整性基准只认 AFC 的 `st_size`**：IC 的 `Progress.totalUnitCount` 和 PTP 的 `byteSize` 对大视频长期偏大，拿它们判 `size < expected` 会把"其实已经取完"误报成「取回不完整，再试一次」。下载函数要把 `(received, planned)` 带回来，`planned == 0` 就跳过校验。
- **IC 那条没有取消通路**：`ICCameraFile.requestDownload` 只给 60 秒兜底，换目标时旧的还得继续跑。做法是传 `isCancelled` 闭包（`DeviceFiles.previewToken()` + `isPreviewCancelled(_:)`），`Timer` 0.2 秒查一次，过期就 `progressRef.cancel()` 并删半截文件。
- **预览必须有自己的 AFC 通道 + 自己的队列**（2026-11 修）：`DeviceFiles` 原来只有一条串行 `queue` 和一个 `photoSession`，缩略图、名字匹配、预览全挤在上面。首次进照片页那串缩略图每个都会在 `downloadLocked` 里 `buildIndex()`（枚举整个 `/DCIM`），把队列顶满，预览排在后面 —— 界面表现是"只有转圈、一个字节都没有"，关掉再点别的视频又立刻正常（索引已经建好、队列空了）。现在 `previewSession` + `previewQueue` 单独一条，`downloadByDevicePath` 走它；`prepare()` 失败（设备只答应一条 AFC 会话）就回退共用通道并置 `previewChannelBroken`，不再每次白试一遍。
- 判断预览"卡住"属于哪一类：能看到「正在取回视频」说明 Photos.sqlite 库索引**已经就绪**（`openPreview` 在库没好时直接 return），所以别再把这类现象归到库索引上；库没就绪是另一套门禁（根视图全屏遮罩）。
- **取回顺序改过**（2026-11 实测踩过，日志是 `库里没有这条 → 直接走 IC`）：原来顺序是「库绝对路径 → IC → 名字匹配」，`meta(asset)` 一查不到就掉进 IC 单流，表现为"点下去 1.5 秒一个字节都没有、卡片停在正在等待设备通道"。现在改成 **库绝对路径 → `/DCIM` 名字匹配（AFC）→ IC 兜底**，并且 `meta()` 多一层「数字后缀 + 同扩展名」在库里兜（唯一命中才算）。原因：PTP 报的文件名经常是随机的（实测 `HPQE7329.MP4`），而磁盘上往往就是这个名字，精确名匹配在 AFC 索引里命中率不低。
- 名字匹配这条在预览里也要传 `priority: true`：它第一次会 `buildIndex()` 枚举整个 `/DCIM`，排在整屏缩略图后面同样会"打开没反应"。`DeviceFiles.download(priority:)` 现在用 `previewSession` + `previewQueue`。

### 8.1 读库"卡几分钟"的三个真实原因（2026-11 实测）

排查顺序按这个来，别一上来就怀疑设备慢：

1. **`--fetch-library` 子进程变孤儿**（最常见的元凶）。主进程 Ctrl+C / 强杀后子进程不退出，被 launchd 收养后继续占着 AFC。再启动 App，新子进程连 `SIZE` 都打不出来 → 旧代码干等 15s + 180s ≈ **"读了 3 分钟"**。判定：`pgrep -fl fetch-library` 看到多个进程。手动清：`pkill -f -- --fetch-library`。防护见 §8.2。
2. **主线程被算死**。任何"按名字/后缀查库"的实现在查询里现扫全表都是 O(n)；`meta()` 又被每张资产反复调用，5000² 次字符串过滤直接让界面几分钟不刷新。必须预建索引（`fileNameByDigits`）+ 查询缓存。判定：`cmi-app.log` 长时间没有新行，但进程还活着。
3. **失败没有出口**。`needsLibraryGate` 只认 `libraryIndex == nil`，读挂了它照样成立，而遮罩里只有一个转圈 → 用户永远看到"正在读取相册索引"。现在 `libraryStatus` 非空就切错误态 + 「重新读取」按钮。

正常一份库：`helper exit=0 check=5279 sawSize=true` / `index assets=4926 albums=21`，耗时 10 秒内（296 MB @ 36 MB/s）。看到 `helper exit=15 check=0 sawSize=false` 就是 §8.2 那类问题。

### 8.2 AFC 通道会被自己搞坏：收尾三步 + 单实例（2026-11 实测）

**症状**：库读不出来，`[library] 读取失败`。此时 PTP 枚举、lockdownd 电量/容量、`isLocked` 全都正常 —— 只有 AFC 坏。

**定性手段**（按顺序，30 秒内能分清）：

1. `--probe-afc` → 立刻 `连接失败：读取失败（连接被关闭）` = 设备侧 afcd 直接拒连。
2. `--fetch-library <tmp>` 有没有打印 `SIZE`：
   - 打不出来，进程还活着 → `sample <pid>` 看栈，卡在 `AFCFileRefOpen → AFCReadData → kevent` 就是**设备不回包**（不是我们卡）。
   - 打出 `SIZE 0 1` 且 `COPY BYTES 0 … CHECK 0` → 连上了但每个文件读回 0 字节，同样是设备侧拒绝。
3. 两者都说明：这是**手机的状态**，代码改不了。恢复只有两条：**拔插数据线**、必要时**重启 iPhone**。

**怎么搞坏的**（自己踩的）：`kill -9` 掉卡在 AFC 调用里的子进程；以及同时跑两个 App 实例（命令行起两次没有 LaunchServices 拦着），两边各一条 AFC 连接互抢。iOS 26.7 那边的连接槽就这么脏了，之后所有 AFC 连接一律被关掉。

**现在的收尾（三条通路，缺一条就会再脏一次）**：

- 子进程侧 `Probe.HelperGuard`：先 `AFCConnectionInvalidate`（把另一条线程里阻塞的读放出来）→ 再 `AFCConnectionClose` → 再 `AMDeviceStopSession` → `_exit`，全程不抛异常。
- 退出触发点：`SIGTERM/SIGINT`（`DispatchSource.makeSignalSource`，父进程超时 `terminate()` 或人按 Ctrl+C）、**父进程死亡**（父进程把一根永不打字的管道挂成子进程 stdin，父进程一死子进程 `read(0,…)` 得 EOF）、以及正常读完的 `defer`。`getppid()==1` 只在 `report()` 里检查，卡在第一个 AFC 调用上永远轮不到，别指望它。
- 父进程侧 `LibraryService.stopHelper`：先 `terminate()`（SIGTERM），等 2.5 秒，还不退才 `SIGKILL`；`killStrayHelpers` 也是先 SIGTERM、**等满 2.5 秒**（`pkill -0` 轮询）再 `-9`。400 ms 那种等于硬杀。
- 看门狗 **30 秒**（原来 15 秒）：设备刚枚举完，AFC 首个回包常要 10 秒以上，一急就 SIGTERM 一个正卡在 `AFCFileRefOpen` 里的子进程 —— 每次失败都赌一次「优雅收尾能不能救回来」。

**单实例**：`SingleInstance`（`flock` 在 `~/Library/Application Support/cleanmyiphone/instance.lock`，进程退出内核自动释放，不会留死锁文件）。第二个实例会激活已有窗口后退出。测试时用 `CMI_LOCK_PATH=/tmp/x.lock` 把锁挪到可写目录 —— 沙箱里 `~/Library` 写不进去，`open` 失败会静默放行，看起来像没生效。

- iPhone 的 `.MOV` 把 `moov` 索引放在**文件末尾**，所以不存在"边下边播"——AVPlayer 必须拿到完整文件才能起播（iMazing 也是全程下载完再播）。想做渐进播放只能自建随机读代理 + remux，量级完全不同。

### 8.3 「数据不对 + 缩略图只出一部分 + 通道被关掉」是三个不同的毛病（2026-11 实测）

一次会话里同时出现这三个现象时，别当成一个 bug —— 它们各自有独立成因，但会互相放大。

**A. 数据不对（视频偏小、应用与数据虚高）**

- 出口在 `AppStore`：`mediaVideoBytes` 在 `libraryIndex` 为空时退化成「PTP 枚举到的资产求和」，而 `appsBytes = 已用 − 媒体 − 系统 − 回收站`，于是**视频一小、应用与数据就被反推虚高**，两个数永远一起错。现在界面看 `mediaBytesReady`，没就绪就显示「读取中…」/「—」。
- 源头是**「读了一半当成成功」**：helper 的 `CHECK > 0` 只说明「主库 + 当时的 WAL 自洽」，不说明「和 `SIZE` 一致」。AFC 半死时每个文件都会「成功地」只读回一部分；只要主库上次 checkpoint 之前的内容还在，`quick_check` 过、`ZASSET` 有行，一份**缺 WAL 尾巴**的旧库就被当成功。`ServiceError.incomplete` 原来从来没抛过。现在父进程拿 `PROGRESS` 终值 和 `SIZE` 对账，差 > 0.5%（或 512 KB）直接抛 incomplete，copy 都不会发生，旧快照保住。
- 核对口径（2026-11 实测一台）：`PASS` 时 helper 应打 `SIZE 0 <总和>` 且 `COPY BYTES` 三项之和 == 总和；本机 296,828,928 + WAL 4.3 MB + SHM 32 KB + 499 B ≈ 301,2xx,xxx，`CHECK 5286`（照片 4889 / 视频 397，视频合计约 71.5 GB）。**数对不上就是没读全**，别怀疑 SQL。

**B. 缩略图只出一部分（照片、视频都有）**

看 `~/Library/Application Support/cleanmyiphone/thumb-log.txt`，一行一类：

| 行 | 含义 | 说明 |
|---|---|---|
| `req <名字> <字节>B photo/video` | 发起请求 | 网格里的格子各自发 |
| `device-thumb <名字>` | 设备端缩略图成功 | **最好的情况**，视频只有这条路 |
| `ok(照片) <名字> <N>B` | AFC 下原图 + 降采样成功 | 慢但能用 |
| `fail(照片) … err=下载不完整 A/B` | 判「没下全」被删 | 多半是**误判**，见下 |
| `fail(照片) … err=DCIM 里找不到 X` | 名字匹配失败 | `lastError` 是共享字段，可能串到别的资产上，别照字面信 |

实测统计（一台机器、一次会话）：256 次请求里只有 12 次 `device-thumb`，98 次 fail。两个真因：

1. 设备端缩略图超时一刀切 **1.5 秒**，连续 3 次超时就 `thumbCircuitOpen` 熔断「本次会话不再试」。刚进照片页设备还在枚举，回一张要两三秒 → 熔断几乎是必然的 → **视频全空**（视频没有 AFC 兜底）。现在按种类给超时（照片 3 秒 / 视频 8 秒），熔断阈值 8 次，并且熔断 **30 秒后放一次探路请求**（熔断是让开，不是判死刑）。
2. 照片兜底拿 **PTP 的 `asset.byteSize`** 当「读到没有」的判据。这个数对不少文件偏大：`downloadLocked` 读循环按它判尾会空转 4 秒，回来上层再拿它比 `onDisk < byteSize` → 判成 `下载不完整 69075/1025001`、删文件、格子永远空。现在 `downloadLocked` 返回 `Downloaded(url, received, plan)`，`plan` 取 **AFC 的 `st_size`**（`entrySize`），PTP 大小只在拿不到时兜底。

**C. 「手机的文件通道被系统关掉了，AFC 没响应」**

判定：`/tmp/cmi-library.log` 只有 `helper 30s 内没给出 SIZE，已终止`，`/tmp/cmi-app.log` 是 `读取失败：…（AFC 无响应）`。这时连四个文件的 `SIZE` 都量不出来 —— 不是慢，是设备侧 afcd 拒服务。

- **先确认设备现在是好是坏**：`--probe-pd`（0.2 秒列出 `/PhotoData` 四个目录 = 好）→ `--fetch-library /tmp/x/Photos.sqlite`（9–10 秒、`CHECK > 0` = 好）。好就说明拔插/重启已经救回来，问题在代码的动作序列。
- 会把它搞脏的动作，按危险度排：`kill -9` 卡在 AFC 调用里的 helper > 15 秒就 SIGTERM 收尾 > **只 open 不 stop 的会话泄漏**（解锁轮询每 2 秒一次、通道探针每轮一次，全在失败路径上）。`isDeviceLocked` / `probeAFCOnce` / `fetchDeviceStats` / `deviceStatsOffMain` / `refreshScreen` / `DeviceFiles.Session.reset` 现在都要关干净。
- **并发不是元凶**：实测两条 AFC 同时读（一条 296 MB 下载 + 一条列目录）互不影响。所以别为了"避免抢通道"去做全局串行化，重点是「用完关掉」和「重抓前先让开自己的连接」（`retryLibraryOnce` → `releaseDeviceFiles()`）。

### 8.4 缩略图：直接读设备自己的缓存（`/PhotoData/Thumbnails/V2`）—— 从"几十秒"到"几毫秒"

结论先写：**不要问 PTP、不要为了缩略图下原图。** 设备自己维护着一套缩略图缓存，AFC 直接读。

```
/PhotoData/Thumbnails/V2/<ZDIRECTORY>/<ZFILENAME>/5005.JPG
  .../V2/DCIM/109APPLE/IMG_9570.HEIC/5005.JPG    33,052 B    3 ms
  .../V2/DCIM/109APPLE/IMG_9810.MP4 /5005.JPG    57,625 B    4 ms
```

- **`ZDIRECTORY` 自带前缀**（`DCIM/109APPLE`；iCloud 那批是 `PhotoData/PhotoCloudSharingData/20971474735/<uuid>/100CLOUD`），和 `V2/` 下的一二级目录一一对应。**不要再拼一个 `DCIM/`** —— 会变成 `V2/DCIM/DCIM/109APPLE`，全不命中。
- 末级文件名通常是 `5005.JPG`（实测 300 条里 299 条命中）。不确定时列一次 `V2/<dir>/<name>` 取最大的 `.JPG`。
- 视频同样有（`IMG_9810.MP4/5005.JPG`），所以"视频缩略图只能等下整片"这个结论是错的。
- 实测（`--probe-thumbs`，2026-11，iPhone 14 Pro / iOS 26.7）：按库索引拼路径 **299/300 命中，平均 7.0 ms、平均 65 KB**。整屏 100 格 ≈ 亚秒级，而原来走"PTP 主动请求"要 1.5 秒/张、串行、连续 3 次超时就熔断；照片兜底还要下整份原图（DNG 能到 72 MB）。
- `Thumbnails/` 顶层还有 `*.ithmb`（例：`3324.ithmb` 168 MB）和 `VideoKeyFrames/` —— 那是旧格式和视频关键帧，不要去解析 ithmb。
- iMazing 的依据：`imazing-reverse/FILESYSTEM.md` 的 `/PhotoData/Thumbnails/V2`、`index/paths_abs.txt:387`。

### 8.5 「不管怎么退出都不留痕」的四条通路

进程被杀的方式决定它能做什么，所以按能力分层，缺一层就会漏：

| 退出方式 | 能做多少 | 谁负责 |
|---|---|---|
| ⌘Q / 菜单 / 点窗口红点（`applicationShouldTerminateAfterLastWindowClosed = true`） | 完整清 | `applicationWillTerminate` → `AppStore.purgeOnTerminate()` |
| `kill <pid>`、Ctrl+C、关机信号 SIGTERM/SIGINT/SIGHUP/SIGQUIT | 完整清（跑在 DispatchSource 队列上，可以安全用 Foundation） | `PurgeGuard` |
| 崩溃 SIGSEGV/SIGBUS/SIGABRT/SIGILL | 只能 `unlink` 固定文件（异步信号安全），目录靠下次启动 | `PurgeGuard` / `CrashTracer` 的 handler |
| `kill -9`、断电 | 进程没有任何执行机会 | **下次启动第一步**的 `purgeLocalDataOnDisk()` |

要点：

- 信号 handler 不在主线程，`purgeOnTerminate()` / `purgeLocalDataOnDisk()` 必须标 `nonisolated`，否则 Swift 6 直接编译不过（`call to main actor-isolated static method in a synchronous nonisolated context`）。
- 启动那一次清理**不能删**：它是 `kill -9` 的唯一兜底。正常退出时上一轮已经清干净，所以这一步"什么都不用删"，不会白删东西。
- 想验证：`CMI_DEBUG=1` 启动后看 `/tmp/cmi-app.log` 有没有 `[purge] 启动清理上次非正常退出的残留：…`；`kill -TERM` 之后 `ls ~/Library/Application\ Support/cleanmyiphone/` 应该只剩 `battery-dump.txt` / `device-dump.txt`（这两个只有机型与键名，不含照片数据）。

### 8.6 「有些视频缩略图不出来 / DCIM 里找不到 / 设备没回数据」的完整解释（2026-11 实测）

先量化，再猜原因。两个探针就够：

- `--probe-videos`（全量审计）：4932 条资产里 **4930 条**能从设备缓存拿到缩略图；只有 2 条视频
  （`IMG_9301.MP4`、`IMG_1771.MOV`）在 `/PhotoData/Thumbnails/V2/...` 下**根本没有条目**，
  而它们的原片是完好的（224 MB / 373 MB，`AFCFileRefOpen` 返回 0，`st_size` 正常）——
  也就是"设备自己没给这两个视频生成缩略图"。这类只能给占位，点开预览仍能播（走 AFC 原片）。
- `--probe-thumbs`：按库索引拼 V2 路径的命中率与耗时（299/300、7 ms）。

其余"DCIM 里找不到 / 取不到这张图（设备没回数据）"不是缓存问题，而是 **asset → 库没对上**：

1. PTP 报的文件名经常是随机的（`HPQE7329.MP4`），库里的 `ZFILENAME` 是 `IMG_7329.MP4`；
2. 视频的 PTP `byteSize` 长期不准，所以"体积 + 时间"那层基本必 miss；
3. 于是 `downloadOriginal` 跳过 AFC 绝对路径 → 名字匹配也找不到 → 掉进 IC 单流 → 几十秒后回不来。

四层匹配（`AppStore.resolveMeta`）：名字 → 数字后缀+同扩展名 → 体积+时间 ±2 秒 → **时间 ±2 秒 + 同种类**（唯一命中）。
最后一层实测能把 396 条视频里的 372 条定位回来；剩 24 条是真的同秒/相邻秒录了多个视频，**有歧义就不猜**——宁可走慢路，也不能把 A 视频的元数据安到 B 上。

### 8.7 一个藏得很深的 bug：SQLite 列类型不固定

```
select typeof(ZDATECREATED), count(*) from ZASSET group by 1;
→ integer|2328
  real|2958
```

`SQLiteDB.Row.double()` 以前只写 `values[key] as? Double ?? 0`：integer 那 2328 行直接变 `0`，
也就是 **2001-01-01**。后果：按拍摄时间排序、按时间筛选、"设备上有新照片就让快照过期"、
影子资产的日期，全都在这 2300 多条上错，而界面上看不出任何异常（数字都"有值"）。

现在 `int/int64/double` 三向兼容（`Int64 → Double`、`Double → Int64`、`NSNumber` 兜一层）。
排查同类问题的手法：**先用 sqlite3 看 `typeof()` 分布**，别假设一列只有一种类型；
再对着 App 里数出来的值比一遍（例如 `--probe-videos` 打印的窗口时间是 `@0` 就是这条路）。

### 8.8 PTP 会话自己断掉以后：删除整批失败 + 界面永久转圈（2026-11-01 现场）

现场长这样：勾了 46 项放进回收站 → 点「彻底删除」→ 界面写「成功 0 项，失败 46 项，设备未连接」，
同时照片页停在「正在读取照片目录」，顶栏刷新按钮**一直是转圈禁用态**，⌘R 没反应，
拔插数据线也没反应；重启 App 之后一切正常（但内存里的回收站标记全丢）。

**三条证据，按这个顺序查**：

1. `~/Library/Application Support/cleanmyiphone/thumb-log.txt` 尾部
   （`tail -3`）：最后一行是 `no-thumb …（设备端缓存没有，PTP 未回数据）` 且**时间戳不再往前走**
   → 设备侧已经不再回 PTP 数据。这条最快，一眼定性。
2. `AppStore.scanStageTitle`：`!catalogDone` → 「正在读取照片目录」；
   `isScanning = !scanFinished && !usingFixture`；`maybeFinishScan()` 要求 `catalogDone`。
   PTP 不回来 → `catalogDone` 永远 false → `isScanning` 永远 true。
3. `PTPBridge.delete` 的 `guard let camera else` → 整批直接退回「设备未连接」，**一项都没碰设备**
   （所以手机上文件是完好的，可以放心重试）。

**为什么拔插数据线没用**：`PTPBridge.start()` 有 `guard !started else { return }`。
上一轮 `stop()`/`start()` 没配对时（或 browser 已经死了但 `started` 还是 true），
browser 根本没在跑，拔插产生的 `didAdd` 没人接 —— App 收不到「设备又插上了」。

**两道兜底（0.1.1 起的写法，别再退回去）**：

- **扫描必须有时间闸**：`AppStore.scheduleScanDeadline()`（30 秒）挂在 `startScan` /
  `connectRealDevice` / `beginSession` 三处（幂等，`finishScan` 里 cancel）。
  到点还没 `catalogDone` 就强制收尾 + 写一句可操作的原因（「读不到照片目录：解锁 iPhone 后点刷新重试」）。
  没有这道闸，**刷新按钮会跟着 `isScanning` 一起被永久禁用**，用户连自救的按钮都点不到。
- **删除前自己重连**：`PTPBridge.delete` 开头 `cameraOrReconnect(timeout: 8)` =
  `stop()` → 停 300 ms → `start()` → 每 200 ms 看一次 `camera`；接上之后再等文件表填上
  （**15 秒**，2026-11 由 3 秒改，见 §8.10：3 秒等不到 4500 个文件，空表会让每条都判成
  「设备上找不到」）。这等于把「拔插数据线」搬进 App。仍失败才报「设备未连接（解锁 iPhone 后重试）」。

**遗留 / 没验证到的**：`cameraOrReconnect` 的异常态（browser 半死）没法在真机上复核
（会抢用户正在用的设备），只做过编译与代码走查；最坏情况与修复前相同（照旧整批报错）。
下次真遇到，先在 `thumb-log.txt` 上看时间戳是否停了，再点删除看是否恢复。

### 8.9 删除过程中的可见性与「哪些没删掉、为什么」（2026-11）

用户原话：「删除需要有一个删除中的提示弹窗，不然可能崩溃或者怎么样。而且删除有时候不一定
删得掉，有些成功有些失败，要有具体原因。」三条落地：

**① 界面必须有动静。** `PurgeProgress`（`PurgeEngine.purge(_:onProgress:)` 每批回调两次：
开始删这批之前 / 这批有结论之后）+ `UI/PurgeStatusOverlay.swift` 的 `PurgeProgressCard`。
显示 `第 101–200 项 · 共 600 项`、进度条、正在删的文件名、`已删 x · 失败 y`。
没有这块的时候，设备删 400 张要几十秒，界面一点反馈都没有，用户以为崩了就强退 —— 
强退会把**内存里**的回收站名单丢光（回收站不落盘，见 `TrashStore` 注释）。

**② 设备不回话要有闸。** `requestDeleteFiles` 的 completion 在锁屏 / 通道半死时**不是报错，
是不回**。`PTPBridge.deleteTimeout = 45` 秒到点就用 `VoidOnce` 收尾，把这一批「既不在成功名单、
也没有逐条原因」的项逐条标成「设备 45 秒没有回执」，并置 `DeleteBatchResult.timedOut`。
`PurgeEngine` 见到 `timedOut` **立刻停**，后面几批根本不发，逐条标「没有执行：设备在前面那一批
就没有回执了」。少了这一条，界面上那个「正在删除」会永远转圈。

**③ 失败要逐条、要能说出来。** `DeleteBatchResult.failed` 是 `[(id, message)]`，`message` 只有
三个来源：
- `ICDeleteError` 的**逐条**回调 `deleteFailed` → `PTPBridge.message(forDelete:)` 按关键字分类：
  `ReadOnly`（iCloud 照片 / 优化存储）、`Permission`、`NotFound`、`Cancel`（多半那一刻锁屏）、
  `Unavailable/Disconnect`、`InvalidParam`、`Failed`（被「照片」App 或同步占用）
- 设备文件表里已经查不到 → 「设备上已找不到这个文件（可能已经被删掉）」
- 超时 / 整批报错 → 补到「没回执」的那些项上（**不要再用一条空 id 的整批错误糊过去**，
  那样界面只能说「失败 N 项」）

失败项**不从回收站移除**（`trash.remove(succeeded)` 只删成功的），所以结果单里能一键重试
（`AppStore.retryFailedPurge()`）。

**界面回归怎么跑**（不接真机）：`CMI_FIXTURE=1 CMI_PURGE_DEMO=300 CMI_FIXTURE_DELAY=0.5
CMI_FIXTURE_FAIL=35 ./build/cleanmyiphone.app/Contents/MacOS/cleanmyiphone`
—— `CMI_PURGE_DEMO` 自动标记前 N 项并点一次「彻底删除」，`CMI_FIXTURE_DELAY` 让每批慢一点
（看得清「删除中」），`CMI_FIXTURE_FAIL` 按百分比造失败（看得清逐条原因）。两个注入点只在
`FixtureDevice.delete` 里，真机路径不经过。

**真机还没验的**：超时分支与 `ICDeleteError` 的真实分布（模拟设备是造出来的）。真机上第一次遇到
「删一半失败」时，先看结果单里每条的文案，再去对照 `ICDeleteError` 的实际枚举值补映射。

### 8.10 「手机上删了还显示 / 新拍的不显示 / 回收站删不掉 / 点重新读取卡住」是一条链（2026-11 二次修）

四条现象一起出现时，别再当四个 bug —— 它们共用一条链：**界面那份列表是 PTP 的旧快照，而「刷新」这条路把设备弄丢了**。

#### 根因一：`ICDeviceBrowser` 是一次性的，`stop()` 之后设备回不来

`PTPBridge.stop()` 原来做 `browser.stop()` + `camera.requestCloseSession()`。**2026-11 真机实测（iPhone 14 Pro / iOS 26.7）**：

```
[ptp] stop() started=true
[ptp] start() started=false delegate=self
[ptp] browser.start() 已发出
（此后 30 秒 → 3 分钟，一条 didAdd 都没有；换 3 个新 ICDeviceBrowser 实例各 start 一次也一样）
```

手机还插着、AFC 读库正常（302 MB 读得完），**只有 PTP 永久空掉**，只能重启 App。而旧 `startScan` 就是「`stopPTP()` → … → `startPTP()`」，所以**刷新从来不刷新列表**：它只会把 PTP 弄死，界面上留下的是没被清掉的旧 `assets`。这就是用户那四条现象的共同来源。

现在的规矩：**`stopPTP()` 只用于终态**（切模拟设备、未连接）。刷新、重读库、压缩一律改成只关会话：

- `PTPBridge.pauseSession()`：只 `requestCloseSession()`，不碰 browser。
- `PTPBridge.refreshCatalog()`：解开会话 → 0.4 秒后 `requestOpenSession()`，并且**把 `catalogFinishSent` 清回 false**（不清的话这一轮 `finishCatalog()` 被一次性守卫吃掉 → `catalogDone` 永远不置位 → 只能等 30 秒闸门收尾）。设备会把 `mediaFiles` 重推一遍，`didBecomeReady` 里重新 ingest。
- `cameraOrReconnect`（删除前重连）也不再 `stop()+start()`：camera 为 nil 时只 `browser.start()` 然后等，等不到如实报「设备未连接」。

#### 根因二：刷新时目录回来了，但界面不认

- 刷新**不清 `assets`**：清了但枚举回不来就是一屏空白（试过，比旧列表更糟）。枚举成功时 `onCatalog` 整份覆盖；失败就保留旧列表，由 `noteCatalogStale()` flash 一句「这份列表可能不是最新的，点刷新重新读取」。
- `scheduleScanDeadline` 改**心跳式**：只认「目录安静了多久」（`catalogHeartbeat`，`onCatalog` / `onCatalogFinished` 都打点），读库阶段（`libraryStarted && !libraryDone`）继续等。原来固定 30 秒从会话开始算，重新枚举 4541 个文件时目录明明在稳步往回吐，闸门还是提前收尾，并写一句**假的**「读不到照片目录：解锁 iPhone 后点刷新重试」（日志里 `scan finished` 紧跟 `deadline fired` 就是这么来的）。
- `resetScan` 必须先 `cancel` 上一轮的闸门：它把 `scanFinished` 掰回 false，旧闸几十秒后会「合法地」醒来，把这一轮正在跑的读库当成卡住。

#### 根因三：卡在 AFC 上不下来

- `DeviceFiles.reset(timeout: 3)`：先把新会话换上（`sessionLock` 保护的 ref），再把旧的丢到它自己的队列上去关；关不掉就放手并写 `lastError`。原来是 `queue.sync`，设备不回包时 `Session.reset()` 里的 `closeAFC` 永远不返回 → `releaseDeviceFiles()` 挂在 `await` 上 → 「重新读取」再也走不下去。
- `retryLibraryOnce` 一进去就置 `libraryRetrying`（门禁立刻显示「正在重新读取相册索引」），并加 `libraryRetryInFlight` 挡住连点/自动重试叠加。
- `killStrayHelpers` 放 `Task.detached`，别在主线程等 pkill（最多 2.5 秒冻界面）。

#### 根因四：删除报「找不到」其实是「还没读到目录」

- `PTPBridge.delete` 等文件表**最多 15 秒**（原 3 秒，4500 个文件填不完），并把两种「查不到」分开说：
  - 表是空的 → 「设备的照片目录还没读完（会话刚重建），等几秒再点一次」
  - 表里有东西、偏偏没这一条 → 「设备上已找不到这个文件（可能已经被删掉）」
- 正常情况（表已经满）一秒都不等，行为不变。

#### 根因五：手机上删掉的照片在 App 里还标着「已压缩」，一删就报「找不到条目」

手机上删的照片（尤其是进了「最近删除」的）PTP 不会报 `didRemove`，`assets` 里那条就留着；它又能按名字匹配到相册库里的行（最近删除的行还在 `ZASSET` 里），于是 `compressionDisplay` 认出了「原图 + 副本」的配对 → 界面上那张幻影照样带「已压缩」角标。再点删除：文件表里查不到 → 以前一律报「设备上已找不到这个文件」，**留在回收站里出不去**，用户只能卡在这里。

现在：删除结果里把这种情况单独标成 `gone`（`DeleteBatchResult.gone` → `DeleteOutcome.gone` → `PurgeReport.goneIDs`）：
- 文件表**空**（目录还没读完）→ 仍然报「等几秒再点一次」，因为那确实可能是一次有效删除；
- 文件表**有东西、偏偏没这一条** → 判 `gone`：不算失败、不重试，**直接从 `assets`、`convertedAssets`、缩略图、回收站里一起移除**，结果单写「另有 N 项设备上已经不存在（多半是在手机上删掉的），已从列表和回收站移除」。

判定依据只有一条：**文件表非空**。所以「会话刚重建、表还没填」的那几秒仍然走失败分支，不会被误判成「已经删掉了」。

#### 真机实测（2026-11-02，iPhone 14 Pro / iOS 26.7）

`CMI_DEBUG=1 CMI_AUTO_REFRESH=1` 跑一轮，日志：

```
[library] 从设备读完整库，库索引就绪（门禁撤）
[ptp] browser.start() 已发出
[ptp] didAdd 金费清的iPhone
catalog 0 progress 0.0 → catalog 4541 progress 1.0 → scan finished
[selftest] 自动触发一次刷新（startScan）
[library] 从设备读完整库，库索引就绪（门禁撤）      ← 刷新这条路上库真的重读了
[ptp] refreshCatalog：重开会话
catalog 4541 progress 1.0 → scan finished            ← 目录也真的重推了，没有假错误、没有闸门抢跑
```

界面侧同时确认：概览 226.29 GB / 5,204 项、照片页 4,164 项 · 20.94 GB、缩略图正常；退出后数据目录与 `/tmp` 日志全空、无 helper 残留。

**没验到的**：`releaseDeviceFiles` 的超时分支（要设备真的卡在 AFC 读里才触发）、`pauseSession` 在「PTP 会话真正打开」时的表现（这一轮测试里 `requestOpenSession` 一直回「请解锁」，因为手机在被无人值守地跑）。下次现场遇到「刷新后列表还是旧的」，先看 `/tmp/cmi-app.log` 里 `refreshCatalog` 之后有没有新的 `catalog ... progress`。

### 8.11 压缩成功后 52 项全删不掉：「设备未连接」，但手机明明没问题（2026-11 现场）

现象：压缩跑完（52 张全成功、副本进了相册），原图按流程进了回收站；一点「彻底删除」，
**52 项全报「设备未连接（解锁 iPhone 后重试）」**，解锁再试还是同样。手机没锁、数据线没动。

#### 根因：压缩的最后一步会把 PTP 打死

压缩必须让相册认出副本，所以最后一步是 `PhotoDaemon.restartLibrary`：
`devicectl` 把设备上的 `assetsd` 和「照片」App **terminate** 再 `launch` 回来。
设备这一下被 ImageCaptureCore 报成 `didRemove` → `PTPBridge.camera = nil`，
而 `ICDeviceBrowser` 是一次性的（见 8.10 根因一），**之后不会再把同一台设备报 `didAdd`**。
于是 `PTPBridge.delete` 一进来就是 `camera == nil`，整批一项都没试就全失败。

要命的是它和 8.10 那条「`stop()` 之后回不来」是同一类，只是触发者换成了设备侧重启服务 ——
**不是用户设备的问题**，报「解锁 iPhone」纯属误导（解锁没用，拔插数据线才有用）。

#### 现在的做法

1. `PTPBridge.cameraOrReconnect(timeout:)` 重写：**camera 为 nil 时换新实例重开浏览器**
   （`browser.stop()` → `replaceBrowser()` → `browser.start()`，8 秒一轮、最多 20 秒）。
   原来是只 `browser.start()` 干等 8 秒 —— 浏览器活着时那是空操作，等于白等。
2. `AppStore.runCompressionStation` 末尾：`combined.daemonRestarted` 为真就**立刻**
   `await ptp.cameraOrReconnect(timeout: 25)`，别等用户去回收站撞墙；没接回来就 flash
   「相册服务重启打断了 PTP 通道，拔插一次数据线再删原图」。
3. 失败文案改成「PTP 通道没回来（相册服务刚重启过，或手机在锁屏）：拔插一次数据线，再点重试」
   —— **拔插数据线**是 8.10 实测唯一有效的恢复手段，解锁不是。

#### 现场救急（不用重启 App）

拔插一次数据线 → PTP 重新 `didAdd` → 回收站点「重试失败的 N 项」即可。
⚠️ **不要退出重开 App**：回收站/压缩站名单只在内存里，退出就全丢，那 52 项的原图就再也定位不到了
（手机上文件还在，但 App 里那份名单没了）。

## 十、往设备回写照片：三条直路全封，但「写 DCIM + 改库」是通的（2026-11 实测）

**结论改口（2026-11 二次修）**：三条「直路」（Airlock / `com.apple.afc2` / `ICCameraDevice.requestUploadFile`）确实全封，但**旁路是通的**，压缩功能现在就走它：把副本文件写进 `/DCIM`，再改 `Photos.sqlite` 登记一条资产、重启 `assetsd`。手机上相册确实能看到（用户实测）。代价和细节见 **§10.5**。下面三条直路的实测结论依然有效，别再回头试。

| 通道 | 结果 | 说明 |
|---|---|---|
| `Airlock` 服务 | ❌ `status = -402653150` | 即 `0xE8000022`，AMD **服务受限**。三个候选名（`Airlock` / `com.apple.mobile.airlock` / `com.apple.airlock`）同一错误码 |
| `com.apple.afc2` | ❌ 同一错误码 | 越狱通路 |
| `ICCameraDevice.requestUploadFile` | ❌ `Upload files failed.` | 头文件 `IC_DEPRECATED("Sandbox restrictions prohibit writing directly to device hardware", macos(10.4,14.0))` —— 只是 deprecated 不是 unavailable，但设备侧确实不认 |

对照组 `com.apple.afc` 正常（根目录 21 项、`/DCIM` 45 个子目录可读），所以不是会话问题。

### 10.1 为什么「删得掉、看不到」

- 删除走 `camera.requestDeleteFiles(...)` = PTP 的 **DeleteObject 协议操作**，设备自己删，相册当然同步
- 往 `/DCIM` 塞文件 = 只写字节，没人通知照片库；相册读的是 `Photos.sqlite`，**不扫目录**

删除是「告诉 iOS 去做」，写入如果只是「瞒着 iOS 放文件」，iOS 就当没发生。

——**这句话正是 §10.5 的做法**：既然相册只认 `Photos.sqlite`，那就把文件塞进 DCIM 之后，自己去改库。

### 10.2 两条被否决的备选

- `Media/PhotoData/Mutations/DCIM/<目录>/<IMG_xxxx>` 里是一堆**空目录**（设备自己的修改锁），不是外部投递口。mutation 文件是 `NSKeyedArchiver` 私有归档，格式错了会污染整个照片库，不要碰
- `Media/Photos/` 是 iTunes 照片同步目录，本机**空的**，`/Photos/Sync` 打不开 —— 同步机制从未初始化

### 10.3 顺手挖到一个有用的东西

`PhotoData/Metadata/DCIM/<目录>/` 里每张照片都有两份**标准 JPEG**：

```
IMG_9810.JPG   83 KB   带完整 EXIF（日期/GPS/机型）
IMG_9810.THM   15 KB   缩略图
```

比原图小一个数量级。以后要做离线比对日期/GPS，读这个比拉原图快得多。

### 10.4 四条探针（换 iOS 版本后一分钟重验）

```
--probe-airlock    列 Airlock 及备选服务、/PhotoData 各目录
--probe-upload     造一张粉色测试图试 PTP 上传
--probe-livefiles  列 DCIM 里「图 + 同名视频」配对，确认实况布局
--probe-livefetch  从库取实况、拼 .MOV 路径、下载一条验 AVPlayer 能不能播
```

### 10.5 压缩回写的真实代价：每批一次 302 MB 双向 + 列表要自己补

实现：`PhotoConversionEngine`（`Core/Conversion/`）

1. 原图按 AFC 下载 → ImageIO 缩放重编码 → **写进同一个 `/DCIM/<目录>/`**（名字 `原名 (1).HEIC`，不覆盖原图）；
2. 整批跑完后**只改一次库**：`fetchFreshDB()` 重新抓一份当前的 `Photos.sqlite`（+WAL+SHM）→ 用 `ConversionDB.apply` 插入资产行（新 PK、`ZADDITIONALASSETATTRIBUTES`、`importedBy = local.cleanmyiphone.qNN` 之类）→ 整份写回 `/PhotoData/Photos.sqlite.new` → `rename` 覆盖 → 删 `-wal` / `-shm` → `PhotoDaemon.restartLibrary()` 让 `assetsd` 重读库。

**为什么必须整份写**：iOS 没有登记资产的公开接口；SQLite 是单文件，AFC 只能整文件覆盖，没有「局部写」。所以**哪怕只压缩一张 1 MB 的图，也是 302 MB 下 + 302 MB 上**。能省的只有两点，都已经在做了：

- **一批只写一次**（不是每张一次）：`run(...)` 结束才进「改库」阶段；
- 界面上给了开关「写回手机相册」：关掉就 `writeDB: false / restartDaemon: false`，副本只落在 DCIM，手机相册看不到，本 App 照样能看到、能预览（省掉那 300 MB 往返）。

**为什么压缩完 App 里「没有新照片」**：新文件是我们自己写进 DCIM 的，设备的目录快照里没有它，PTP 不会报出来（`refreshCatalog` 也只会重推旧的 `mediaFiles`）。所以转换成功后 `AppStore.injectConvertedCopies(result)` 用转换记录（文件名、目录、字节、像素）直接**补进 `assets`**，并在 `onCatalog` 里 `mergingConverted(list)` 按 id 去重合并 —— 不用等设备认。

**两步流程：先标记，后执行（2026-11 用户定的）**

既然写库是「每批 302 MB、压一张也是这个价」，那第一次点「压缩」就**不该真的压**。现在：

1. 照片页选中 → 「压缩/转换」面板只有参数（比例 / 格式 / 质量）→ 按钮是**「标记压缩」**：写进 `CompressionQueue`（**只在内存**，和回收站一样），格子给**灰色完整三件套**「待压缩」（灰环 + 18% 灰铺 + 左上角灰胶囊带压缩图标，和标记回收同一套，只换颜色；蓝色不能用 —— 蓝色就是选中色），侧栏「设备 › 压缩站」显示条数，底栏 flash 一句「这一步不动设备」。
2. 「压缩站」里二次确认 → `runCompressionStation(writeBack:)`：按**参数分组**跑（不同比例/格式各一组，**每组一次写库**，顶栏写「N 组参数」），成功的移出名单、失败/跳过的留着能再点；**没有「写回手机相册」开关**（2026-11 用户定的：压缩完必然要写回，不进相册等于没压），一律 `writeDB:true` + 重启 `assetsd`。压缩站页面和回收站同构（搜索 / 排序 / 升降序 / 网格⇄列表 / 框选 / 底栏批量）。
3. 视频不进压缩站（暂不支持），已在回收站的项也不进；标记回收时会把同一张从压缩站里拿掉。

**结果卡的「省了多少」原来算错**：旧代码在转换结束（`clearSelection()` 之后）再从选中里捞原图大小，捞到 0 → 「节省」变成负数、显示「体积增加 332 KB」。现在 `ConversionRecord.originalSize` 在转换时就把原图体积带出来，结果卡写三段：`副本合计 X（原图 Y）` + `彻底删除后净省 Y−X`。

**体积怎么算才对**：当前这一刻设备上是「原图 + 副本」两份都占着，所以看上去是**变大**（副本那点）；真正省下来要等你把标记的原图彻底删除。别把这两个状态混在一句文案里。

⚠️ **所有探针必须 `stopSession`**。只 `closeAFC` 不关会话，设备上会漏一串会话，漏够了开始拒连，现象是 `--probe-afc` 之后一律「连接被关闭」，恢复只能拔插数据线。这个坑第一次写探针时又踩了一次。
